# 📞 Calling Service WebApp

Современное веб-приложение для видеозвонков с поддержкой WebRTC, оптимизированное для Telegram WebView и native wrappers (iOS/Android).

## 🌟 Основные возможности

### 🎥 Видеозвонки
- ✅ **Групповые звонки** - до 5 участников одновременно
- ✅ **WebRTC (P2P)** - прямое соединение для минимальной задержки
- ✅ **Адаптивные раскладки** - автоматический выбор оптимального отображения
- ✅ **Быстрое создание** - звонки по ссылкам с 6-значным кодом

### 🔒 Безопасность
- ✅ **End-to-End шифрование** - AES-256-GCM шифрование видео/аудио кадров со случайным IV
- ✅ **Ключи не проходят через сервер** - обмен ключами по P2P data channel (DTLS)
- ✅ **Ротация ключа** - при выходе участника ключ перевыпускается
- ✅ **Fail-closed** - кадр, который не удалось зашифровать, никогда не уйдёт открытым
- ✅ **Insertable Streams / RTCRtpScriptTransform** - шифрование на уровне кадров (Chrome, Firefox, Safari)
- ✅ **Синхронизация ключей** - автоматическая передача ключей новым участникам
- ✅ **Серверная валидация** - формат кодов комнат, лимиты участников, rate limiting
- ✅ **Лимиты по IP** - число соединений и число «прощупываемых» комнат в минуту
- ✅ **Проверка Origin** - WebSocket принимает апгрейд только со своего origin
- ✅ **Resume-токены** - переподключение без возможности подделать чужой clientId
- ✅ **Security-заголовки** - CSP, X-Content-Type-Options, Referrer-Policy, HSTS

### 🎨 Режимы отображения
- **Grid (Сетка)** - все участники равного размера
- **Spotlight (Фокус)** - один большой, остальные миниатюрами снизу
- **Sidebar (Сайдбар)** - основное видео слева, миниатюры справа
  (на телефонах миниатюры уходят под основное видео)
- **Compact (Компакт)** - собеседники во весь экран, своё видео в углу
- **Auto (Авто)** - автоматический выбор в зависимости от количества участников

В режимах Spotlight и Sidebar крупную плитку занимает собеседник, а не
собственная камера. Пока в комнате никого нет, все режимы показывают обычную
сетку.

### 🏓 Пинг-понг во время звонка

- ✅ **На двоих, прямо в звонке** — приглашение отправляется участнику, поле
  появляется под видео, звонок продолжается
- ✅ **Полностью peer-to-peer** — игра идёт по тому же data channel, что и ключи
  шифрования; сигнальный сервер не видит ни байта и ничего о ней не знает
- ✅ **Без рассинхрона** — симулирует тот же участник, который делает WebRTC-оффер
  (роль выводится из `clientId`, отдельное сообщение не нужно и переживает
  переподключение). Второй шлёт только позицию своей ракетки и предсказывает её
  локально, поэтому управление не «плывёт»
- ✅ **Управление** — палец или мышь по полю, на десктопе ещё и стрелки
- ℹ️ Поле рисуется от лица игрока: своя ракетка всегда ближняя, как если бы вы
  сидели с другой стороны стола

### 🎭 Система реакций
- ✅ **10 эмодзи** - ❤️ 👍 😂 😮 😢 🔥 🎉 👏 💯 🚀
- ✅ **Летающая анимация** - красивые эффекты появления
- ✅ **Звуковые уведомления** - приятные звуки при отправке
- ✅ **Счетчики популярности** - отслеживание самых используемых реакций
- ✅ **Сортировка** - автоматическая сортировка по популярности

### 🔊 Управление звуком
- ✅ **Индивидуальная громкость** - настройка громкости для каждого участника (0-200%)
- ✅ **Вертикальный слайдер** - компактный дизайн регулятора
- ✅ **Визуальные индикаторы** - бейджи с текущим уровнем громкости
- ✅ **Web Audio API** - маршрутизация через gain node с лимитером, чтобы
  усиление выше 100% не уходило в клиппинг
- ℹ️ Настройки громкости живут только внутри звонка: идентификаторы участников
  одноразовые, хранить их между звонками нечего
- ⚠️ **Safari и iOS**: WebKit проигрывает удалённый поток через Web Audio как
  тишину, поэтому там звук идёт напрямую из видеоэлемента, а поштучная
  регулировка сводится к «выключить/включить» — WebKit игнорирует громкость
  медиаэлемента

### 📱 Адаптивный дизайн
- ✅ **Полная ширина на десктопе** - использование всего экрана на больших мониторах
- ✅ **Мобильная оптимизация** - удобный интерфейс на смартфонах
- ✅ **Адаптивные сетки** - от 2 до 4 колонок в зависимости от ширины экрана
- ✅ **Увеличенные элементы** - большие кнопки и шрифты на десктопе
- ✅ **Breakpoints**: 768px (mobile), 1024px (desktop), 1440px (wide desktop)

### 🌐 Интеграция
- ✅ **Telegram WebView** - CSP разрешает встраивание со страниц `*.telegram.org`
- ✅ **Шаринг в Telegram** - кнопка отправки ссылки (в webview, где `window.open`
  заблокирован, ссылка кладётся в буфер обмена)
- ✅ **Темная тема** - автоматическая поддержка темной темы
- ℹ️ **Mini App SDK не подключён** намеренно: `telegram-web-app.js` — сторонний
  скрипт, а CSP страницы (`script-src 'self'`) держит на ней только свой код,
  потому что в этой же области видимости живёт ключ шифрования. Чтобы включить
  полноценный Mini App (`ready()`, `expand()`, темы), добавьте тег скрипта в
  `public/index.html` **и** `https://telegram.org` в `script-src` в `server.js`

### Важно для production:

1. **HTTPS обязателен** - WebRTC требует HTTPS для доступа к камере/микрофону
2. **WebSocket** - Убедитесь, что ваш хостинг поддерживает WebSocket
3. **Порты** - Настройте через `process.env.PORT` (по умолчанию 3000)
4. **TURN серверы** - задаются через переменные окружения `TURN_SERVER_URL`,
   `TURN_USERNAME`, `TURN_PASSWORD` и раздаются клиентам через `GET /config`.
   Без собственного TURN звонки будут работать только там, где хватает STUN
   (большинство домашних сетей), но не за строгими корпоративными NAT
5. **`TRUST_PROXY`** - число прокси-хопов перед приложением, **по умолчанию 0**.
   Его нужно выставить явно (Railway/Render — обычно `1`), иначе лимиты будут
   считаться по адресу сокета. Значение должно точно соответствовать
   инфраструктуре: лишний хоп позволит подделать `X-Forwarded-For` и обойти
   лимиты, поэтому «угадать» его сервер не пытается

```javascript
const TelegramBot = require('node-telegram-bot-api');

const TOKEN = 'YOUR_BOT_TOKEN';
const WEB_APP_URL = 'https://your-domain.com'; // URL вашего веб-приложения

const bot = new TelegramBot(TOKEN, { polling: true });

bot.onText(/\/start/, (msg) => {
  const chatId = msg.chat.id;

  bot.sendMessage(chatId, '📞 Добро пожаловать в сервис видеозвонков!\n\n' +
    '✨ Возможности:\n' +
    '• Групповые звонки (до 5 человек)\n' +
    '• End-to-End шифрование\n' +
    '• Реакции и эмодзи\n' +
    '• Индивидуальная громкость\n\n' +
    'Нажмите кнопку ниже для начала:', {
    reply_markup: {
      inline_keyboard: [[
        {
          text: '📞 Создать звонок',
          web_app: { url: WEB_APP_URL }
        }
      ]]
    }
  });
});

bot.onText(/\/call/, (msg) => {
  const chatId = msg.chat.id;

  bot.sendMessage(chatId, 'Запуск звонка...', {
    reply_markup: {
      inline_keyboard: [[
        {
          text: '📞 Открыть',
          web_app: { url: WEB_APP_URL }
        }
      ]]
    }
  });
});
```

4. Установите зависимости и запустите:

```bash
npm install node-telegram-bot-api
node telegram-bot.js
```

## 🔒 Безопасность и шифрование

### E2E шифрование

Приложение использует **AES-256-GCM** шифрование на уровне кадров
(**RTCRtpScriptTransform** в современных Chrome/Firefox/Safari, легаси
`createEncodedStreams` в старых Chrome/Edge):

1. **Генерация ключа** - 256-битный ключ из CSPRNG (Web Crypto API)
2. **Шифрование кадров** - каждый видео/аудио кадр шифруется индивидуально
3. **Случайные IV** - для каждого кадра генерируется случайный 12-байтовый IV
4. **Обмен ключами через P2P** - ключи передаются только по DTLS-шифрованным
   data channel напрямую между участниками; сигнальный сервер их не видит
5. **Fail-closed** - кадр, который не удалось зашифровать, отбрасывается,
   а не отправляется открытым
6. **Маркировка кадров** - зашифрованные кадры помечаются заголовком, поэтому
   включение/выключение шифрования не ломает видео в переходный момент

### Модель угроз (честно)

- ✅ **Пассивный** сигнальный сервер не видит ни медиапотоки, ни ключи: ключ
  ходит только по DTLS-шифрованному data channel между участниками
- ✅ Участники не могут подделать `senderId` (выставляется сервером) или
  чужой `clientId` при переподключении (resume-токен с HMAC)
- ✅ Вышедший участник не расшифрует то, что пошло после его ухода: владелец
  ключа перевыпускает его на каждый `peer-left`
- ⚠️ **Активный** (скомпрометированный) сервер MITM-ит звонок: он ретранслирует
  SDP, а значит может подменить DTLS-фингерпринты и встать между участниками —
  и тогда ключ кадров придёт уже ему. То есть E2EE здесь защищает от
  подглядывания сервером, но не от сервера, который вмешивается. Полное
  решение — сверка отпечатков вне канала или ключ в фрагменте ссылки
  (`#k=...`, который браузер серверу не отправляет); ни то, ни другое пока
  не реализовано
- ⚠️ Любой, кто знает код комнаты, может войти и получить ключ — код комнаты
  это секрет, делитесь им только с участниками
- ⚠️ Любой участник может выключить шифрование для всех (`e2ee-off`). Смена
  состояния видна по индикатору «Защищено E2EE» и всплывающему уведомлению

### Безопасность кодов комнат

- Генерация 6-значных кодов (A-Z, 0-9) через `crypto.getRandomValues`
  (rejection sampling — распределение равномерное)
- 36^6 = 2,176,782,336 возможных комбинаций
- Сервер принимает только корректный формат кода, ограничивает частоту сообщений
  и число **разных** комнат с одного IP в минуту — это то, что делает перебор
  кодов дорогим (по умолчанию 30 попыток в минуту вместо десятков тысяч в секунду)
- Рекомендуется использовать комнаты разово
- Автоматическая очистка при выходе последнего участника

### Рекомендации

- Включайте шифрование для конфиденциальных звонков
- Не делитесь кодами комнат публично
- Используйте HTTPS в production
- Разверните собственные TURN серверы для критичных применений

### Настройка STUN/TURN серверов

ICE-конфигурация раздаётся клиентам сервером через `GET /config` и задаётся
переменными окружения — credentials не хранятся во фронтенде:

```bash
STUN_URLS=stun:stun.l.google.com:19302,stun:stun1.l.google.com:19302
TURN_SERVER_URL=turn:your-turn-server.com:3478,turns:your-turn-server.com:443?transport=tcp
TURN_USERNAME=your-username
TURN_PASSWORD=your-password
```

### TURN без собственного сервера

Если держать свой coturn не хочется, задайте managed TURN от Cloudflare:

```bash
CLOUDFLARE_TURN_KEY_ID=<из панели Cloudflare>
CLOUDFLARE_TURN_API_TOKEN=<токен этого ключа>
```

Ключ создаётся в панели Cloudflare на уровне **аккаунта** (не внутри домена):
раздел **Realtime → TURN**, прямая ссылка `dash.cloudflare.com/?to=/:account/calls`.

⚠️ В этом же разделе создаются **SFU-приложения**, и их учётные данные выглядят
похоже. Нужен именно «Create a TURN Server app» — он выдаёт **Turn Token ID**.
Если в панели написано **App ID**, это SFU, и TURN API ответит на него
`404 cannot find specified key`.
Тарификация: 1000 ГБ в месяц бесплатно, дальше $0.05 за гигабайт исходящего к
клиенту трафика. Ретранслируется только то, что не прошло напрямую.

Приложение обращается к
`POST /v1/turn/keys/<id>/credentials/generate-ice-servers` и отдаёт клиенту всё,
что вернулось, включая STUN Cloudflare на порту 53 — он проходит там, где
блокируют 3478.

Приложение само сходит к их API за временными кредами и закеширует их. Кеш
здесь не оптимизация, а необходимость: `/config` открыт всем, и без кеша
достаточно обновлять страницу в цикле, чтобы израсходовать квоту API аккаунта.
Если их API недоступен, отдаются последние удачные креды, а при их отсутствии
конфиг просто приходит без TURN — но не ломается.

Свой TURN и Cloudflare можно включить одновременно: клиент получит оба, а
больше кандидатов — больше шансов, что звонок соединится.

**Публичные бесплатные релеи не работают.** `openrelay.metered.ca` не отвечает
ни по UDP, ни по TCP (проверено запросом Allocate) — прописывать его
бессмысленно.

### Настройка максимального числа участников

Через переменную окружения сервера:

```bash
MAX_PARTICIPANTS=5
```

Лимит применяется сервером и сообщается клиентам через `GET /config`.

**Примечание**: Большее количество участников требует больше ресурсов
(mesh-топология: каждый участник соединяется с каждым).

## 🐛 Отладка и решение проблем

### Проверка WebRTC соединения

Откройте Chrome DevTools → Console:

```javascript
// Проверка доступа к медиа устройствам
navigator.mediaDevices.enumerateDevices()
  .then(devices => console.log(devices));

// Проверка WebRTC
console.log(RTCPeerConnection);

// Проверка поддержки шифрования кадров (RTCRtpSender конструктором не создаётся)
console.log('RTCRtpScriptTransform:', typeof RTCRtpScriptTransform !== 'undefined');
console.log('Legacy insertable streams:',
    typeof RTCRtpSender !== 'undefined' &&
    typeof RTCRtpSender.prototype.createEncodedStreams === 'function');
```

### Проблемы с доступом к камере/микрофону

1. ✅ Убедитесь, что используется HTTPS (или localhost)
2. ✅ Проверьте разрешения в браузере (Settings → Privacy → Camera/Microphone)
3. ✅ Проверьте, не блокирует ли браузер доступ к медиа
4. ✅ Попробуйте другой браузер (рекомендуется Chrome/Edge)

### WebSocket не подключается

1. ✅ Проверьте, что сервер запущен (`npm start`)
2. ✅ Проверьте порт (по умолчанию 3000)
3. ✅ Убедитесь, что WebSocket не блокируется firewall
4. ✅ Проверьте консоль браузера на ошибки

### ICE connection failed

1. ✅ Проверьте доступность TURN серверов
2. ✅ Попробуйте другую сеть (возможно блокировка корпоративным firewall)
3. ✅ Используйте iceTransportPolicy: 'relay' для принудительного использования TURN

### Шифрование не работает

1. ✅ Нужен `RTCRtpScriptTransform` (Chrome 128+, Firefox, Safari 15.4+) либо
   легаси `createEncodedStreams` (Chrome/Edge 86+)
2. ✅ Проверьте консоль на ошибки шифрования/дешифрования
3. ✅ Убедитесь, что все участники получили ключ — участник без поддержки
   шифрования отправляет `e2ee-unsupported`, и его медиа у остальных скрыто

### На iOS/Safari не слышно собеседников

Симптом известен и обойдён в коде: WebKit отдаёт тишину, если удалённый поток
идёт через `createMediaStreamSource`. Приложение определяет WebKit и выводит
звук прямо из видеоэлемента. Если звука всё же нет — коснитесь плитки
участника: это и запустит воспроизведение, и разбудит `AudioContext` после
прерывания (звонок, Siri).

### v3.1.0 (2026-08-05)
- 🔊 **Починен звук на iOS/Safari**: удалённые участники были не слышны весь
  звонок — WebKit проигрывает удалённый поток через Web Audio как тишину и при
  этом не бросает исключение, так что запасной путь никогда не срабатывал
- 🎥 **Звонок без камеры**: при отсутствующей, запрещённой или занятой камере
  происходит переход в аудиорежим вместо отказа во входе; сообщения об ошибках

- 🐛 **Утечка комнат на сервере**: `rejoin` со сменой `clientId` не освобождал
  прежнее место — комната навсегда сохраняла мёртвую запись, слот сгорал, а сама
  комната никогда не удалялась (перебором можно было исчерпать `MAX_ROOMS`)
- 🤝 **Устранена гонка при одновременном переподключении**: оферту в паре теперь
  делает строго одна сторона, а offer/answer несут идентификатор сессии, так что
  ответ для уже закрытого соединения распознаётся, а не применяется вслепую
- 🧟 **Неудачный rejoin завершает звонок** вместо «живого» экрана, сигналинг
  которого сервер молча выбрасывает
- 🛡️ **Проверка Origin при WebSocket-апгрейде**, лимиты по IP на соединения и на
  число перебираемых комнат, контроль исходящего буфера, явный `trust proxy`
- 🔑 **Ротация ключа E2EE** при выходе участника; временные TURN-креденшелы
  (coturn `use-auth-secret`) и `Cache-Control: no-store` на `/config`
- 📦 **Статика больше не кешируется на час** — деплой не оставит старый `app.js`
  против нового протокола
- 🎛️ **Раскладки**: крупная плитка достаётся собеседнику, а не своей камере;
  sidebar получил мобильный брейкпоинт; «Компакт» в одиночку не показывает
  пустой экран
- ♿ **Возвращён pinch-zoom** (было `user-scalable=no` — нарушение WCAG 1.4.4)
- ✅ **Тесты**: 66 против 18 (сейчас 100) — добавлены клиентские тесты в jsdom и покрытие
  лимитов; набор больше не завершается через `process.exit`, который прятал
  падения

Часть правок этого релиза — исправления регрессий, найденных адверсариальным
ревью уже внесённых изменений:

- 💥 **Отказ в соединении по лимиту IP ронял весь сервер**: обработчик выходил
  раньше, чем вешался слушатель `error`, и одного некорректного кадра от
  отвергнутого сокета хватало, чтобы убить процесс
- 🚪 **Неудачный rejoin выселял из текущей комнаты**: место освобождалось до
  валидации, поэтому опечатка в коде выбрасывала участника из живого звонка
- 🎥 **Камера оставалась включённой**, если запрос разрешения завершался уже
  после конца звонка
- 🔑 **Ротация ключа E2EE не сходилась** — исправлено упорядочиванием по паре
  (эпоха, владелец)
- 🤝 **Дедлок при потере оффера**: сторона-оферент молчала при коллизии; теперь
  переотправляет свой оффер
- 🔒 **`TRUST_PROXY` больше не угадывается**: значение 1 по умолчанию в
  production отдавало обход IP-лимитов любому напрямую доступному деплою
